## 2. 我们要验证的问题

建立可用于多种企业知识的通用语义骨架，支持领域定义、文档语义提取、语义表与语义图、结构化/全文/向量检索、原文证据读取及 Wiki 生成。

这里的通用性是：不同企业共享存储、加工、治理与检索机制，使用不同的业务类型、属性、关系、术语及规则。不是承诺一个模型无须领域信息就能理解所有行业。

必须至少用三个领域验证，先做汽车。其他两个领域尚未由 Jacky 最终确定；政务政策、企业制度/业务流程只是候选。不能用三个汽车子主题代替三个不同领域。

汽车验证范围覆盖整车、三电、底盘制动、车身安全、热管理、智能驾驶、维护、试验与召回；不限定轮胎轮辋。

## 3. 三个 Codex 窗口与权限边界（已确认）

| 窗口 | 角色 | 工作和产物 | 禁止事项 |
| --- | --- | --- | --- |
| 第一窗口 | 产品开发者 | 开发本项目，提供通用骨架、构建与检索能力、文档和 MCP；形成可固定版本的产品 | 将行业逻辑偷偷写死在核心代码；把人工补数据库当产品能力 |
| 第二窗口：Jacky + Codex | 知识库开发者 | 只基于产品文档和公开接口分析资料、定义领域、编写领域资产、试构建、检查、修正及发布知识库 | 修改产品代码、产品内部 Schema 或直接修内部表；依赖阅读内部实现才能完成任务 |
| 第三窗口：Jacky + Codex | 知识库使用者 | 根据已发布知识库提问、多轮检索、读证据、形成回答与反馈 | 修改领域定义、触发知识库写操作、直接修改产品或内部数据库 |

Jacky 会同时扮演知识库开发者和使用者，但两个入口、权限和验收记录要分开。

建议使用独立工作目录、开发者与使用者分别连接的 MCP 服务或凭证，以及独立数据库角色。文件目录约定和 Agent 提示词不是安全隔离；产品服务必须执行读写权限。第三窗口不暴露构建、发布和定义写工具。

产品固化后，第二、第三窗口的缺口通过问题记录交回第一窗口。第一窗口修复后发布新的产品版本，重新验收。不得在领域目录里放修改核心产品的脚本、隐藏插件或旁路 SQL 来掩盖缺口。

## 4. 面向知识库开发者的产品体验（已确认方向）

不要要求 Jacky 先理解本体、图模式、YAML 或数据库设计。

开发者应能从以下输入开始：

1. 一组资料及其来源范围。
2. 知识库用途和适用对象。
3. 想回答的真实问题，以及明确不应该编造的答案。

产品和开发者 Agent 分析样本，提出候选领域定义，展示原文与提取结果；开发者通过具体业务例子纠正。只向用户询问影响业务含义且不能可靠确定的歧义，按共同原因归组，避免逐条审核海量记录。

例如问“标称容量和可用容量是否分别保留”，而不是问“请定义汽车本体”。资料或产品规则已经能确定的事项，应自行处理并保留依据。

领域配置确实需要机器可读表示、Schema 校验和版本，但格式由产品设计确定。此前讨论的 `domain.yaml`、`glossary.yaml`、`dream.md`、`retrieval.md`、`evaluations.yaml` 是职责示意，不是要求初学者手工填写五个文件，也不是冻结的最终格式。

可提供文件优先的开发入口及 MCP，暂不强制建设图形界面。必须支持 Agent 发现规范、读取示例、生成候选、校验、试运行、检查差异及修正。配置不得携带任意 Python/SQL 代码变相获得产品写权限；执行性扩展另行设计授权边界。

## 5. 产品内置骨架与领域资产的分工

以下是逻辑职责，最终表结构由设计收敛。

### 5.1 产品内置

- 领域定义的注册、校验、版本和作用域。
- 稳定对象身份及别名；缺少身份字段时保留未决候选，不能用同名强行合并。
- 带条件、时间、单位和适用范围的声明；对象引用和值的类型化表达。
- 有类型的关系、事件及参与者；避免只能表达无条件二元三元组。
- 固定来源版本与页/段/块/表格等定位、摘录、指纹和证据支持关系。
- 来源原文陈述、试验观测、计算结果、模型推断及人工确认状态的区分。
- 提取运行、候选、冲突、核验、确认、构建、发布和失效记录。
- 检索、证据读取、派生产物、增量更新和版本一致性。

### 5.2 知识库开发者产生的领域资产

- 对象、属性、关系、事件等业务定义，以及术语、别名、单位和枚举。
- 业务身份与合并规则、提取目标、适用条件、证据要求及确认点。
- 检索与回答策略、Wiki 主题组织、代表性问题和验收数据。
- 业务确认和纠错记录。

汽车中的车型、车型配置、电池包、电机、制动系统、试验和召回，均属于领域定义。不得在核心表名、API 分支或业务校验代码中硬编码。

### 5.3 语义表、图、索引和 Wiki 的一致性

建议以有来源的语义记录作为权威事实表示，图和 Wiki 从这些记录派生；避免让 LLM 分别独立生成互相不一致的表、图和 Wiki。图查询结果必须能回到对应声明及证据，不能只有图可视化。

一个声明允许多个来源支持；撤回一个来源时不能删除仍有其他来源支持的事实。不同工况下的不同数值未必矛盾，真正冲突必须显式保留。记录有效期和来源/系统更新时间应区分。

向量是相似性检索工具，不代表事实判断或证据定位。Wiki 帮助理解和导航，不替代原始证据。

## 9. 两套 MCP 合同（能力要求，名称待设计）

### 开发者 MCP

发现产品规范与示例；创建知识库；登记/导入来源；分析样本和提出领域候选；提交及校验领域资产；预览抽取；查看候选与证据；处理冲突与确认；触发构建、查询进度与错误；运行验收问题；检查版本差异；发布与回退。

长任务返回任务 ID，后续查询可得到具体阶段、失败原因及可恢复状态。重复提交应有幂等规则；失败不能用泛化“成功入库”掩盖。

### 使用者 MCP

了解已发布知识库的范围和定义；按对象、类型、属性、条件、时间过滤；查询关系路径；混合召回；按稳定引用读取原文及必要上下文；查看发布版本与限制；提交反馈。

不提供直接执行任意 SQL、读取任意本地路径或修改知识库的工具。生产化权限以后扩展，但原型必须证明只读身份不能调用写能力，也不能跨知识库读写。

每次任务绑定明确知识库和发布版本；后续取证不能静默跳到最新版本。读取仍检查当前授权。LLM/Agent 的计划和解释与工具实际执行结果分别记录。

## 10. 验收标准：三个角色分别验证

### 产品提供者

- 汽车领域类型、问题和规则来自领域资产，而非产品核心代码。
- 固化产品版本、文档、MCP Schema、配置规范及数据库迁移版本。
- 至少三个不同领域在公开合同下工作；新增领域不要求定制核心表/检索分支。确需改产品时记录缺口、升级产品版本，并重跑已有领域回归。
- 跨库隔离、开发/只读角色、版本引用、构建失败恢复和错误说明有真实验证。

### 知识库开发者（第二窗口）

- 在独立工作区，仅使用文档和开发者 MCP，从用途、资料和问题开始建立领域。
- 不要求先手工写完整 Schema；系统/Agent 能提出候选并以样例协助确认。
- 能查看原文、对象、声明、图关系、冲突、Wiki 和构建差异，并通过修改领域资产纠错。
- 不读取内部实现、不修改产品代码、不手工修表；记录实际操作轨迹和首次使用阻碍。

### 知识库使用者（第三窗口）

- 不看内部数据库或产品源码，仅使用使用者文档和 MCP 完成真实问题。
- 覆盖跨文档实体关联、条件过滤、关系遍历、版本差异、表格数值/单位、冲突及资料不足。
- 关键结论能回到正确源版本及原文位置；明确区分实测、计算和推断。
- 对复杂设计影响题，证据不足时能回答“目前不能确定、缺少什么”，不能编出百分比或因果关系。
- 权限拒绝、无答案、歧义澄清和错误反馈属于正式验收，不只检查成功 HTTP 响应。

对照：同一批资料和问题，比较简单全文/向量召回与增加语义表/图后的答案正确性、证据覆盖、条件保留、耗时、Token 与成本。由人工确认的答案/证据作为基准，不允许同一模型既生成答案又作为唯一裁判。数值阈值与样本规模待设计中提出并与 Jacky 收敛。

图能力至少要有问题必须通过关系/条件组合才能正确回答，并展示实际查询及依据，不能用“生成了一张图”作为验收。Wiki 要验证正文引用、来源变更后更新以及与记录的一致性。

## 11. 建议推进次序（不是已批准的实现细节）

1. 审计本地环境、现有资料与模型服务；提出最小产品设计和工具合同，明确未决问题。
2. 固定通用记录骨架、领域资产职责、角色与发布合同，设计首批汽车问题基准。
3. 打通真实链路：原件 → MinerU → 有证据候选 → 核验 → 语义表/图 → 索引/Wiki → 发布 → 检索及证据读取。
4. 提供外部 Agent 可独立使用的文档与 MCP，运行第二、第三窗口验收；产品修复后再固化版本。
5. 在同一产品版本上完成另外两个领域；记录通用性成立和不成立的证据。
6. 原型验证后再规划 Lakebase/LakebaseFS 集成；不把本地成功等同生产能力或产品发布。
