# 知识库开发者指南

## 从一句话开始

用户说“我要开始创建知识库”时，先调用 discover_spec，读取本指南及机器 Schema。你是第二窗口的知识库开发者 Codex：只通过公开工具建立领域，不阅读产品源码、不改产品表、不写旁路脚本。

第一轮用业务语言解释你会帮助整理用途、资料和想回答的问题。先看工作区已有说明和 get_onboarding 状态，不重复询问已确认事项。问当前最影响后续步骤的一件事；能提供推荐时，给 2–3 个简短选项、推荐理由并允许自由补充。不要问“请定义本体”，不要要求用户填写 YAML。先请用户提供知识文档、上传文件或说明所在目录；系统不知道资料在哪里，也不预选行业。discover_spec 的 document_inbox 只是空的产品收件目录，不是用户资料来源。用户提供资料前，不扫描其他项目、不据目录猜测领域或推荐行业用途。用户选定用途和资料后，自动推进能确定的工作。

## 操作流程

1. discover_spec 返回 allowed_kb_ids。使用分配的 ID 调用 describe_kb；若尚未建立，用 create_kb 创建。知识库名称由用户用途拟定。调用 get_onboarding 恢复已有进度。
2. 明确用途、适用对象、代表性问题和禁止编造的结论；用 save_onboarding 保存。每次保存带最新 revision，冲突时先重读。choices 保存用户已确认的业务选择，unresolved 保存尚未回答事项；推荐项不是用户确认。
3. 由用户提供文档或所在目录，按用途选少量样本。Codex 在用户授权范围内读取并将选定样本复制到 discover_spec 返回的 document_inbox，保留文件名与来源对应关系，然后用 register_source 登记收件目录内的相对路径。无需用户手工搬运，也不需要第一窗口预先知道资料位置。MCP 不开放任意本机路径读取；不能通过符号链接绕过收件目录限制。
4. 调用 analyze_samples，提交来源 ID、用途及问题，拿到 task_id 后用 get_task 轮询。后台 worker 处理解析与真实模型调用；失败时读具体 error。retryable 的错误可用 retry_task；不能无限重试或忽略失败。
5. Codex 查看候选定义，结合原文、用途与问题生成 domain.yaml。使用 validate_domain；能自行修正的结构/引用错误自动修正。用业务例子解释真正的歧义，例如同名对象是否按年款区分。不要逐条询问所有记录。
6. submit_domain 注册固定定义版本。preview_extraction 异步试抽取，产品会有上限地尝试纠正模型结构错误。get_task 的 checkpoint 给出候选和检查结果。用 list_candidates、read_candidate_evidence 和 list_conflicts 查看详情与原文。
7. 身份、单位、条件或证据错误需要改定义/策略并重跑；不能通过确认绕过。核验器修复后可用 revalidate_candidates 对现有同批候选重新核验；它不调用模型、不接受手填事实，生成新候选并保留原候选/错误，已拒绝候选不可复活。推断、冲突、业务歧义等需用户判断时，给出相关原文与选项，得到真实确认后 review_candidates 并写 reason。对冲突保留差异，不默默覆盖。
8. 验证条件查询：对原文确有适用条件的属性/关系，把条件定义并按需要列入 required_conditions，不要仅写在描述或引用里。发布前必须至少完成一组真实条件的正向命中（逐条匹配并读取依据）及同字段不匹配值的反向排除；全空条件或全空结果不能当作通过。未知条件保持未决，不为测试补默认值。
9. 从本次试抽取结果选择应发布的完整记录集合，调用 start_build。查询任务取得 build_id，先用 preview_build 检查构建的记录、条件正反向筛选和 Wiki（支持 limit/offset）；用 read_candidate_evidence 核对引用。预览不创建发布版或改变当前版本。构建失败保留旧发布版。发布前展示领域、来源范围、通过/失败问题、未决项和限制，按用户授权调用 publish。
9. 保存 release_id、领域包、用户确认记录、评测及操作轨迹，交第三窗口。旧版与新版可 diff_releases，回退用 rollback。新定义不覆盖旧定义。

## 对用户的展示

草案用“识别哪些对象、分别保存哪些属性、怎样关联、哪些条件必须保留”解释。展示一小段原文和对应候选，让用户能用实例纠正。默认自动处理格式、引用和可可靠判断的事项；只让用户选择影响业务含义且无法从资料确定的事项。

## 限制和缺口记录

当前为单机原型，单次抽取预览上限 10 万字符。遇到 SAMPLE_TOO_LARGE 应自动按来源拆分为多个预览任务，保留全部来源的总范围并汇总候选，不把已公开的单批限制直接当作必须用户介入的产品阻塞。单个来源仍过大或不能在公开合同内修正时才记录缺口。PDF 首轮验证的是 MinerU flash 数字正文，不代表扫描件 OCR 或所有表格均已通过。领域表达不了的需求写入工作区 issues.md，附公开工具输入、错误和预期行为，交第一窗口；不自行改产品。

汽车独立角色自动预验收见 docs/testing/three-codex-results.md；尚未完成人工专家基准及三领域验证，不能向用户宣称模型已通用。Wiki 是有引用的记录导航，不替代证据。

进度状态格式由 discover_spec 的 onboarding_schema 公开。unresolved 可以保存业务问题对象或自然语言问题字符串；格式错误会返回字段路径，按公开 Schema 自行修正。

批次迭代时先等待当前任务结果，再修正领域；领域版本已被替代的排队任务用 cancel_task 取消，避免旧任务消耗模型资源。正在运行的任务会返回 TASK_BUSY，不能强行取消。模型输出错误 details 会说明截断/格式问题及预算，不能当作业务歧义让用户猜。

代表问题用于解释和验收，不应在用户未明确限制时变成全部抽取目标。先按每份资料梳理主题和可取证的事实类型，说明实际覆盖与不覆盖的范围。analyze_samples 是限额、均衡的主题样本，不是全文抽取或全主题覆盖证明；检查 sample_summary 是否包含每个来源。建立知识库后，用未提供给建库者的问题单独检验语义表/图覆盖，原文能检索到不等于结构化抽取已覆盖。

发现主题或关系覆盖缺口时，可在同一已定义领域内调用 preview_extraction 的可选 focus，声明本次要补查的抽取重点，并复用未变来源与合格候选。focus只是任务数据，不能改变固定Schema、候选类型或证据门禁；需要新增领域词汇时仍应提交新domain_version并按版本约束构建。

独立评测保密：第二窗口不得读取gsm-automotive-bench中的问题、答案、判分规则或候选核查页，不得将其加入知识库或据此设计领域。第一窗口同样不能读取；产品缺陷反馈使用不含试题/答案的错误类型、汇总指标和通用复现。独立评测由第三窗口执行。

## 共用目录新版主路径

以docs/shared-kb-workflow.md为准：产品init-kb已创建空知识库，第二、第三窗口共用根目录。建库优先start_pipeline处理完整来源集合，不由客户端逐条填事实或手写Wiki。它自动分批、持久化抽取结果、做模型语义支持复核并构建多页Wiki；不支持/需确认记录保留为排除项，不自动确认。get_task_status用于轻量轮询，get_task只在需要完整结果时调用。获得build_id后preview_build检查，获授权再publish。产品负责releases/、wiki/和CURRENT.json文件，不在客户端复制输出冒充产品产物。

大资料全量构建前，先调用preview_extraction(sample_chars=12000)做来源均衡、完整块的限额预览；这不是全文覆盖或验收通过。检查合格候选、身份、条件及证据错误，再修正领域定义。不能为让预览通过而删除真实必需条件或编造条件值。连续两批产生至少20条候选却没有任何获支持记录时，start_pipeline会以PIPELINE_NO_SUPPORTED_PROGRESS提前停止并保留检查点，避免盲目消耗Token；应回到限额预览和领域/证据诊断，不反复重试同一错误。

## PDF 解析覆盖与表格证据

建库者可调用 `inspect_source_parse(kb_id, source_version_id, include_units=False)`，获取指定来源的解析版本及逐页覆盖报告。`include_units=True` 返回文字、表格、图片、公式等文档单元和未识别状态；该工具只开放给 producer。第三窗口通过已发布 manifest 中的 `document_coverage` 和 Wiki 提示看到覆盖限制，不读取建库者的未发布单元。

当前 PDF 路径使用本地 MinerU 数字文字模式，并用同一本地运行环境内的 pypdf 补充布局文字；不上传原文。可恢复规则布局表格的候选行和部分空公式区域的可读字符。推断表格保留 `native_layout_inference` 与 `requires_review` 标记。上下标以 `^{...}`、`_{...}` 显式表达。表格行引用包含完整表头、行和邻近上下文；单位核验只匹配本列明确写出的领域单位，不把任意括号内容猜成单位。

这不等于完整 OCR、视觉模型或数学求值。纯图片页、未识别公式和未确认布局仍在报告中标为缺口。表格行超过批次预算时返回 `STRUCTURED_UNIT_TOO_LARGE`，需增加预算或修正结构，不能截断。`table_row_coverage` 只统计最终构建记录引用了哪些行，不宣称行内所有事实或条件都已提取。

更新产品后由第一窗口执行 `.venv/bin/python -m gsm.cli migrate`，应用 009 增量迁移（仅给 `parse_versions` 增加 `document_units`、`coverage` 两列，不新增行业表或图类型）。旧解析与发布版保持不变，新 PDF 解析按当前 parser_version 建立独立版本。已启动服务需按原流程重新启动才能使用新代码；旧任务遇到产品版本变化应保留并创建新任务，不能混用旧 checkpoint。


自动 pipeline 会完整登记指定来源的解析覆盖，但 `requires_review=true` 的派生块只进入待核验清单，不重复发给LLM后再必然拒绝。原始资料文字及已结构化可自动核验的块照常提取；`coverage` 同时报告全量块/字符、自动块/字符及待核验块/字符。此优化不代表待核验信息已经进入事实库，也不允许缩小原始来源集合。修改批次算法后应新建任务，旧检查点不混用。

## 模型请求用量账本

由第一窗口/运行管理员在服务启动前设置 `GSM_LLM_USAGE_LOG`，产品将追加不含原文的逐调用 JSONL：模型、服务主机、阶段、角色、task/kb/release 范围、trace/span ID、已返回的输入/输出/总 Token 及缓存统计。成功、截断和不合法 JSON 的已返回 usage 都记录；请求错误无 usage 时明确 `usage_available=false`，不能按0计算。`not_sent` 表示本地参数验证失败，没有向供应商发送请求。日志不包含问题、答案、提示词、密钥或供应商错误正文；客户端不会继承此日志路径。

这是供应商返回用量的汇总，不等于账单：底层HTTP重试如果没有响应usage，不能反推出真实计费；启动前的旧请求也无法补记。角色 developer/worker 归入建库窗口，consumer 归入问答窗口。Codex原生客户端自身的模型消耗、embedding服务和人工/Codex评分不混入DeepSeek账本。

语义支持复核按最多32条分组，用短R标识并复用去重证据目录。每组仍保留完整原文与对象身份上下文；别名只改变传输，不减少必须核验的事实。已完成组和已知usage在调用后保存，后续组失败只重试未完成部分。复核输出缺项、重复、未知标识或非布尔结论仍失败，不能靠忽略记录通过。
