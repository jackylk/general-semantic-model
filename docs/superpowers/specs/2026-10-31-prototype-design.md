# 通用语义模型本地原型设计

状态：待 Jacky 评审。2026-10-31。

## 目标与边界

验证同一产品是否能通过领域资产承载三个不同领域，并相较全文/向量检索改善有条件、跨文档问题的回答。先做汽车，另两个领域建议政务政策、企业制度，尚待用户确定。原型成功不等于覆盖所有行业或已具备生产能力。

已确认：第一窗口开发产品；第二窗口的 Codex 通过产品规范和开发者 MCP 定义领域、构建发布；第三窗口通过使用者 MCP 查询。第二窗口不需要阅读内部实现，不允许修改核心代码或直接修表。使用本地 PG、文件、指定 Embedding 和 deepseek-flash，不连接云服务或修改其他项目。

## 方案比较与选择

采用通用记录骨架＋声明式领域资产，用户已认可该方向。自由图谱抽取难以约束身份、条件和发布；逐行业编写代码无法检验通用性。前者保留为抽取候选手段，后者不能作为领域接入方式。

以下技术栈为开发者提议，尚非用户已确认：Python、Pydantic/JSON Schema、PostgreSQL、pgvector、独立任务工作进程和 Python MCP SDK。单仓库、一个数据库与本地文件仓库，不引入 RAGFlow 全栈或独立图服务。依赖版本实施时锁定。

## 第二窗口怎样定义领域

### 引导式入口与自动化（用户已确认）

补充确认：通用建库入口不知道用户知识文档在哪里，不预绑定任何外部资料目录或行业。先请用户提供文件或目录；Codex 在其授权范围内将选定样本复制到工作区空的 documents 收件目录后登记。收件目录属于产品存储入口，不代表已有用户资料。汽车实验资料目录仅属于第一窗口的实验背景，不能作为第二窗口默认输入。

第二窗口完成一次最小启动配置后，用户只需说“我要开始创建知识库”，Codex 即应通过工作区启动说明和 MCP 发现入口读取开发者指南，开始引导知识库开发者定义领域。交付独立领域工作区模板及启动说明，使引导可被新窗口发现，不能依赖第一窗口的聊天记忆。

流程依次了解用途、资料位置与代表性问题，自动分析样本，提出领域草案，用原文和业务例子说明对象/属性/关系/条件，再自动生成领域包、校验、试抽取与修正。资料和规则能确定的事项自行处理并保留依据；影响业务含义且无法确定的事项才询问用户。每轮集中处理一个主题，给出少量易懂选项、推荐项和理由，并允许自由补充；不向用户展示数据库设计题或要求手写 YAML。

可恢复的引导状态、已确认选择、依据、未决项和下一步保存在独立领域工作区及相应产品审核记录中，新窗口可继续，不重复询问已确认事项。候选生成、校验和预览尽量自动运行；不能以自动化绕过冲突、身份和证据门禁。发布前展示具体构建差异、验收结果与限制，按用户已有授权执行；自动推进不等于自动确认业务歧义。

角色验收必须包含从“我要开始创建知识库”开始，仅靠启动说明、产品文档和公开 MCP 完成领域开发。记录用户被要求做出的选择、人工修正次数及阻塞，检验引导是否有效，而非只验收文件能否提交。

产品提供版本化规范、完整小示例、错误说明及 MCP 资源。第二窗口先提交用途、来源范围、目标问题和禁止臆测事项；Codex 读取样本，通过产品的候选分析工具得到领域草案，再编写和提交领域包。

领域包入口为 domain.yaml（以 JSON Schema 校验），包含类型、身份字段、属性和值类型、关系、事件角色、规则、术语、单位、条件维度、来源适用性、抽取和确认策略；大段提取/检索说明及评测样例可引用包内文件。文件名只是机器入口，用户不必手工填写。包禁止可执行 Python、SQL、动态插件和任意外部路径。

校验分为语法、类型引用、身份完整性、单位和条件规则、代表性样例试跑。错误返回字段路径、原因、相关样例和修正建议。支持预览差异，已发布定义不可就地覆盖。第二窗口只纠正领域包或提交审核决定；表达不了的要求形成产品缺口。

首版支持字符串、布尔、精确十进制、枚举、日期/区间、数量与单位、对象引用、列表；条件支持有类型的比较、集合、区间及 all/any 组合。业务规则是可保存、可检索的条件与结论，不承诺任意程序执行或完整逻辑推理。

## 通用记录与存储

知识库、领域版本、来源及来源版本、解析版本/块、对象及身份候选、声明、关系、事件及参与者、规则、证据、候选审核、冲突、运行、构建、发布、反馈为固定产品职责。业务类型通过定义 ID 引用；核心中禁止汽车表名或汽车特判。

声明保存主体、谓词、类型化值、条件、有效期、来源陈述/观测/计算/推断类别及审核状态。身份不足保留未决，不能仅凭同名合并。证据是记录到来源版本的多对多支持；撤回来源只撤销该支持，仍有有效支持的记录继续存在。冲突比较要考虑条件、单位、时间和适用范围，不能把不同工况当矛盾。

关系和事件支持有界图遍历；每一步返回记录 ID、条件和证据。首版使用关系表与递归 SQL，限制深度、节点数、超时与循环；不开放任意 SQL。图、索引、Wiki 均来自同一批已核验记录。

文件按内容哈希保存，源身份独立于本机路径。原件与解析结构不可变，锚点包含来源版本、解析版本、块/页/表格位置、摘录和指纹；重解析创建新版本。表格保留单元格及表头关联。权限控制覆盖原件、块、记录和派生产物。

全文检索先验证中文分词方案，与原文子串基线比较，不使用默认英文分词冒充中文能力。结构过滤、全文、向量召回做结果融合；向量并非事实核验。Wiki 每项事实引用记录和证据，生成后检查引用及版本，不能自行生成独立事实。

## 解析、抽取与发布

来源登记 → 固定输入 → 解析 → 抽取候选 → 身份对齐 → 结构/证据/条件检查 → 冲突和业务确认 → 构建图、索引、Wiki → 验收 → 发布。

MinerU 通过适配层接入，保留原始结构输出和参数版本。先用本地源码确认 CLI/API、运行环境与许可，再选择后端；不为首条闭环全量解析。RAGFlow 仅参考批处理、证据定位和 Wiki 思路；默认不复制代码。其证据默认 soft 门禁不能作为发布标准：定位成功也不能证明语义正确。

没有可定位证据、身份未决或应确认而未确认的候选不得发布为事实。可发布的推断必须明确标注并保留输入、方法及运行记录。审核可按共同原因归组，但不得无依据批量确认。

首版强制审核触发条件为身份字段不足、冲突、推断、业务含义歧义和领域指定确认项；其余候选只有通过类型、单位、条件和证据检查后才可成为待发布记录，并保留每项检查结果。自动检查通过不标记为人工确认，也不声称证明了业务真实性。

任务使用持久状态、阶段检查点和输入哈希，返回 task_id；同身份、同知识库及幂等键重试复用任务，不同请求体返回冲突。模型调用预算、重试上限、错误和可恢复阶段可查。不得以入库成功代替构建成功。

发布是不可变 manifest，固定来源、定义、记录集合和索引/Wiki 版本。所有产物就绪后，事务切换发布指针；失败保留旧版。回退切换到已有完整发布。查询会话固定 release_id，旧引用不跟随最新版本；读取仍检查当前授权。源更新按依赖关系重建，首版允许整库重建作为正确性回退。

## 两套 MCP 与权限

开发者：discover_spec、create_kb、register_source、analyze_samples、validate_domain、submit_domain、preview_extraction、list_candidates、review_candidates、list_conflicts、start_build、get_task、evaluate、diff_releases、publish、rollback。

使用者：describe_kb、get_definitions、search、query_records、query_paths、read_evidence、get_release、submit_feedback。反馈写入独立队列，不改变权威事实。所有查询绑定 kb_id 与 release_id；返回工具实际结果、限制和稳定引用，不把 Agent 计划算作执行结果。

另提供 retrieve(question, kb_id, release_id)，由产品内 Retrieval Agent 按领域检索策略多轮调用同一组受控查询与证据工具，返回结论、条件、支持记录、引用、未知事项和调用轨迹；轮次、Token 与超时有上限。第三窗口 Codex 可直接求证或调用 retrieve，但不承担产品内部唯一的检索实现。对照实验分别固定相同的 Agent 编排及预算，仅改变可用的检索能力，避免把不同编排效果归因于语义模型。

接口具体参数通过 Pydantic Schema 生成并固化；公共错误包含 code、message、details、retryable、task_id（适用时）。开发者只能导入已配置来源根目录中的文件或已登记上传对象；使用者不能读取任意路径。

分别启动开发者和使用者 MCP，凭据绑定角色与允许的知识库；服务端再次鉴权，使用者端不注册构建工具。PG 使用独立角色并以知识库策略限制记录访问；测试直接越权调用、跨库 ID、伪造引用与任务 ID，不能仅测试工具列表隐藏。域资产不提供任意执行权限。

## 本地环境与未决配置

已实测 Embedding 请求成功、1024 维；Docker、psql、uv 可用。现有两个 postgres:17 容器分别占用 54722、54727，不复用或改动。默认本地 PG socket 无响应。建议新建本项目数据库容器，绑定 127.0.0.1:55438；审计时该端口无监听，启动前再次检查。

deepseek-flash 的 provider、base URL、真实 model ID、结构输出及凭据来源待核实，禁止打印环境凭据或假定模型别名等于官方模型。缺配置时明确报告，不能用 mock 冒充真实抽取。

汽车目录清单的 186 份 downloaded PDF 已逐项检查路径和大小，无缺失或大小不符；尚未重算 SHA256，资料适用性仍需检查。第一轮选择约 12 份有代表性的文档/片段，覆盖多系统、表格、扫描件、版本、参考设计与量产资料的差异。全部保存选择理由和解析失败记录。

## 实验与交付

建议汽车先建立 40 道人工核验问题：直接事实、条件/单位、跨文档身份关联、关系路径、版本/冲突、无答案各类均覆盖。至少 8 道确需关系和条件组合的问题；按文件划分开发与留出集，先冻结答案及证据，再运行比较。后两个领域各建议 20 道，最终题目和阈值需用户确认。

对照 A 为相同资料的全文/向量检索，B 增加语义记录与图，保持模型、问题和回答预算一致；分别报告答案正确性、引用定位与支持性、条件保留、拒答、耗时、Token、费用以及构建成本。人工或领域专家是最终裁判，模型评分仅辅助。

建议最低门槛：权限与固定引用测试全部通过；已回答关键结论均可定位正确证据；测试中无无依据数值/因果结论；语义方案必须在组合问题上展示可核验收益，不能以总平均分掩盖退化。数值质量目标在小批次人工基准完成后冻结，不事后调整以宣称成功。

第一窗口交付固定产品版本、迁移、可复现启动、无密钥配置样例、规范、两份角色手册和 E2E 证据。第二窗口在独立工作区仅用公开合同建汽车知识库，记录首次操作障碍；第三窗口仅用使用者入口完成盲测。另两领域使用同一产品版本，若必须升级核心，记录原因并重跑已有回归。未完成三领域前，只能宣称汽车闭环或局部验证。

## 推进顺序

1. 确认本设计及 LLM 接入配置；建立独立仓库、依赖锁和本地数据库。
2. 实现定义规范、证据/版本/权限骨架和公开合同，用小文本夹具验证边界。
3. 接入真实 MinerU、LLM、Embedding，完成汽车小批次与发布检索闭环。
4. 固化文档与版本，交第二、第三窗口独立验收并修复产品缺口。
5. 同版本验证另外两个领域，形成支持或否定通用性的实验报告。
